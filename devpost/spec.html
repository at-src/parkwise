Build With AI: Basics · Technical Spec

ParkWise

The blueprint: a single browser page, Three.js for the 3D scene, a hand-written kinematic bicycle model for the car, geometric checks for parking, and a coach that demonstrates then guides. No framework, no bundler, no services.

● Spec draft — for review

In Plain Language

Open the page → a tiny Node server hands over index.html → it loads Three.js and one main script. Three things then run together:

① The scene

Three.js draws the street/car-park, parked cars, curb, line markings and the learner's car, with four switchable camera views.

② The car "brain" (physics)

A kinematic bicycle model: position, heading, speed, steering angle. It moves like a real car — pivoting around the rear axle, front wheels at their Ackermann angle.

③ The coach

Watches the car vs. the spot, computes distances, shows guidance near the car — and can drive a correct sequence itself to demonstrate.

Why this shape

Smallest honest proof. A full physics engine is heavier and less accurate for walking-pace parking; no build tools means it's fast to run and record.

Components (each maps to a PRD behavior)

Scene & rendering Core Journey · Look and Feel›
Builds the Three.js world (ground, curb, markings, parked cars, learner car), lighting, renderer, and the animation loop. Feeds the camera system and places the learner's car each frame from the physics.
Car model — kinematic bicycle physics Driving the car›
Holds { x, z, heading, speed, steerAngle } and advances it from current inputs using bicycle-model geometry. Exposes the footprint for collision/parking checks.
Input handler Driving the car›
Reads arrow keys / WASD → throttle (forward/reverse) + steering intent. Possible mouse support decided at build.
Camera system Camera views›
Four views — top-down, in-car/seat, chase, free isometric — switchable without disturbing the car or its state.
Coach — demonstrate + guide The coach›
Guide: computes distances (car ahead/behind, offset from the line), renders guidance near the car, updates live.
Demonstrate: feeds the car model a correct control sequence so it parks itself; yields control on Practice.
Parking check — pass/fail Parking check›
At rest, tests the footprint against markings and obstacles: within the lines, roughly straight, not touching → success. Otherwise no success.
Scenario & reset Reset and scenario switching›
Defines a set of common scenarios (parallel, reverse bay, angle as the core set): start pose, obstacles, bay — each a data entry, so more can be added later. Reset returns to start; switching rebuilds the scene.
Sound optional Sensor sound›
Web Audio API beeps, rate increasing as the nearest obstacle approaches. Included if it fits.
UI overlay Screens and Layout›
Plain DOM over the canvas, CSS-styled: Practice, camera toggle, reset, scenario toggle, success verdict.

Stack & Run

Stack
  • Vanilla JS (ES modules) + HTML + CSS — no framework, no bundler
  • Three.js r0.183, vendored in lib/ (no CDN)
  • Hand-written kinematic bicycle model (no physics engine)
  • Geometric overlap for collision + parking check
  • Web Audio API beeps (optional)
  • Node http static server (zero deps)
Where it runs
  • Browser (desktop), served locally by Node
  • No keys, no env vars, no external services
  • Start: npm start → open http://localhost:3000
  • Submission = demo video + public GitHub repo
  • Deployment optional; local recording is enough

Risks & the One to Verify First

⚠ Reversing in the bicycle model — verify first

At negative speed the car curves opposite to intuition, and parallel parking is mostly a reverse maneuver. Plan: before building the coach, checks, or scenarios, drive the car in reverse and confirm the rear swings the correct way into the bay. This is also the learning-goal moment (real-world-physics code).

  • Tunneling at speed → cap speed to walking pace and check overlap every frame; sub-step if needed.
  • ES modules via file:// → blank page. Always run through npm start; document it.

What Was Simplified

  • Bicycle model instead of a physics engine — lighter, more accurate for slow parking, and more educational.
  • Geometric overlap instead of engine collisions — enough to judge a park and a bump.
  • A small set of defined scenarios (parallel, reverse bay, angle) instead of a full level editor — each is a data entry, so more can be added if time permits.
  • No persistence instead of accounts/saved progress — the idea needs no memory between sessions.
